# AGENTS.md

Discord bot (C#, .NET 10, Discord.Net 3.20) with virtual-money games, custom commands, reminders, and a local-LLM chat (Ollama). See [FILETREE.md](FILETREE.md) for a navigable file map — read it before searching.

## Solution layout (`DiscordBot/DiscordBot.sln`)
- `DiscordBot/` — main app (exe). Bot, commands, games, services, ASP.NET host.
- `Common/` — shared net10.0 lib: exceptions, helpers, Gist/local file storage. `Common/_nanogpt/` is unrelated Python (nanoGPT); ignore.
- `WebAlerter/` — Strawman trade checker (`StrawmanChecker`); its worker is currently disabled in `Startup.cs`.
- `Tests/` — xunit + Moq (`BlackjackTests`, `GPTHelperTests`, `WebAlerterTests`).

## Commands
```
dotnet build DiscordBot/DiscordBot.sln
dotnet test Tests/Tests.csproj
dotnet run --project DiscordBot
```
CI/CD: `azure-pipelines.yml` runs on the Pi itself (self-hosted pool `Pi`). It installs the .NET 10 SDK (`UseDotNet@2`), publishes linux-arm64 self-contained to a staging folder while the old bot keeps running, then stops the `DiscordBot` systemd service (`DiscordBot/DiscordBot.service`), backs up the files it is about to replace to `/srv/DiscordBot.prev`, copies the new build in and starts it. If the journal shows no Discord.Net `Gateway Ready` line within 5 minutes, or systemd restarts it, the old files are restored, the old bot restarted and the run fails. Save files (`coinaccounts.json`, `stockmarket.json`) are never touched, and live `mappings.json` / `reminders.json` are kept. Pushing to `master` deploys. Still build and test locally before pushing to `master`.

## Env vars (see `Common/Helpers/EnvironmentHelper.cs`)
`DiscordBotToken`, `GITHUB_PAT_TOKEN`, `GITHUB_USERNAME`, `GITHUB_GIST_ID`, `S_U`, `S_P`, `PORT` (default 5000), `IS_HEROKU`. Never commit secrets.
Gateway intents are set in `Startup.CreateDiscordConfig` (unprivileged + Message Content + Server Members; tested in `DiscordConfigTests`). Message Content and Server Members are privileged and are switched on in the Discord Developer Portal. To add another privileged intent (Presence), switch it on in the portal first, or Discord refuses the connection.
The dungeon deletes players' typed command messages to keep the channel clean. That needs the bot's **Manage Messages** permission in the server. Without it the commands stay, and the dashboard still works.

## Architecture
- Entry: `Program.cs` (Kestrel web host + generic host) → `Startup.cs` (**all DI registration**) → `ChatWorker` (hosted service; starts Ollama installer + `MessageHandler`).
- `MessageHandler` subscribes to Discord events and forwards messages to `CommandManager.RunCommand` (synchronously on the gateway task, so a command that never finishes stops the heartbeats and takes the bot offline; `Services/HangWatchdog` then fails fast after 10 minutes offline or with the minute loop stuck, and systemd restarts it), and buttons, select menus and modals (`ButtonExecuted`, `SelectMenuExecuted`, `ModalSubmitted`) to `RunComponent` / `RunModal` in `CommandManager_Components.cs`, run off the gateway task.
- Interactions: custom ids are `ComponentId.Build(game, action, args)` (`Models/ComponentId.cs`, "game:action:args", 100 chars max); the game prefix routes the click. Discord needs an answer within 3 seconds, so handlers acknowledge first (`DeferAsync()` when a dashboard edit is the answer, `DeferAsync(ephemeral: true)` for private views, or a modal as the very first response), and refusals go back privately (`FollowupAsync(..., ephemeral: true)`). The same gates as typed commands apply (stopped, banned, bots), and game clicks count as money activity for the raffle. Game dashboards are one message edited in place with `Services/LiveMessage.cs`: each frame's images get fresh file names (`Frame.Add` returns the `attachment://` url for the embed), and `BumpAsync` reposts at the bottom of the channel. Clicks on any older message are stale (`LiveMessage.Owns`).
- Slots (`.slots`, `.slot`): rules in `Games/SlotMachine.cs` (three weighted 30-stop reels, line pays by a table; `ReturnToPlayer()` is worked out exactly and tested to stay at 90-96%; three 💎 pay the pool, at least x100 and at most x2000 the bet), text and buttons in `Games/SlotView.cs`, money and animation in `Games/Managers/SlotMachineManager.cs`, handlers in `Managers/CommandManager_Slots.cs`. One machine message per player, owner-only buttons (`slot` prefix: Spin, Bet ½, Bet x2, Max, Bet…, Cash out) and the session lives in memory (30 minutes idle). A spin settles the bet through `BetManager` first and only then shows the result with one instant edit of the message (no spinning frames), so a failed edit can't lose money. Typed `.slots` is deleted after the machine is posted.
- Stats (`.stats [me|@user] [page]`): `Services/StatsReport.cs` builds nine pages (overview, betting, games, stocks, property and debt, jackpot and income, power-ups, dungeon, donations) from `CoinAccountStats` plus a `StatsContext` the command fills in (`CommandManager.StatsEmbed`), with a `stats:pick:<accountId>` select menu that edits the message (public, anyone can switch pages). The counters are updated where the money moves: `BetManager.ResolveBet` (per-game `GameRecord`s keyed by the `game` argument, daily roll, jackpot, bonus, jackpot feed), `StockService` trades and option settlement, `PropertyService` buy/sell/rent/holding costs, `RaffleService` (draws, uses, `Seize`/`Hit`), `CoinService.AddInterest`, `CoinAccounts.PayDebtFrom/RepayFromCash`, `DungeonManager`. New counters start at zero on old accounts. Add a counter by adding a property to `CoinAccountStats`, updating it at the hook and showing it in `StatsReport`.
- Money buttons (`Managers/CommandManager_MoneyButtons.cs`, prefixes in `Models/MoneyComponents.cs`: `stk`, `pu`, `prop`, `debt`, `slot`; blackjack and duck race use their base command, `bj`/`duck`): Buy/Sell on `.stocks` (a pick menu), `.stocks SYMBOL` and trade results; Sell menus and the auto-sell switch on your own `.portfolio`; Use buttons on `.pu` and a My power-ups button on raffle results; Buy a house on `.property`; Join…/Join max (`joinmax`: all your cash, no form)/Start on game lobbies, Play again… on duck race results (opens the bet form), Hit/Stay in blackjack, and on blackjack results Play again (`bj:again`: `BlackjackManager.PlayAgainBet`, the clicker's last bet kept in memory by the base manager, raised to the 10% minimum and held to their cash, then create and start at once; with no last bet it opens the form) and New bet…. They call the same methods as typed commands (`BuyStockText`, `SellStockText`, `BuyPropertyText`, `UsePowerUpText`, `AutoSellText`), so rules and wording match, and results post publicly. Buttons on shared things act for whoever clicks; buttons on someone's own view carry their id and only work for them (`ButtonOwner`). Amounts come from `AmountModal`. Houses are sold by `PropertyHolding.Id` (`PropertyService.SellById`) and kept power-ups found with `PowerUps.FindHeld`, so a list that moved can't hit the wrong one.
- `CommandManager` is a **partial class** split across `Managers/CommandManager_*.cs`:
  - `_Main` — constructor, the `_commands` list, `RunCommand` parsing/dispatch.
  - `_Games` — roulette / blackjack / faceoff handlers.
  - `_Methods` — all other command handlers (largest file).
  - `_Bot` — bot-to-bot commands (`.initiatebet`, `.resolvebet`, `.lbjson`).
- Commands use prefix `.`; each is `Command(name, handler)` with `Description`, `Syntax`, `Hidden`, `RequiresAdmin`. Handler signature: `Task X(DiscordSocketClient, SocketMessage, List<string> args)`.
- Games: `Games/<Game>.cs` (rules) + `Games/Managers/<Game>Manager.cs` (session/lobby, derives `BaseMultiplayerManager`) + `Games/Models/` (players, cards, bets). The base manager takes a `GameContext` (user, channel, guild; `GameContext.From` a message or an interaction) rather than a message, and runs every change under one lock (`Locked`), since typed commands and button clicks run on different threads. A game's messages go through `AnnounceLobby`, `AnnounceStart` and `AnnounceResults` (the defaults post a message each time, as duck race does). A game with a slow animation sets `AnimateInBackground` (duck race, a replay of seconds): `Start` returns at once and `AnimateAndContinueAsync` replays it without the lock, then takes the lock to pay out, so the gateway and the other commands are never held (`DuckRaceBackgroundTests`). Blackjack overrides them to keep one table message per channel (`BlackjackManager.Publish`, text in `Games/BlackjackView.cs`) edited from the lobby through the hands (Hit/Stay) to the results, and deletes typed `.bj` commands where it can.
- Feature flag: `AppSettings.PrestigeDisabled` (appsettings.json, default `true`) disables `.prestige`, prestige scaling of interest/daily income/bonus threshold. Interest is `Constants.InterestPercentage` (2%).
- Dungeon (`.dng`): rules in `Games/Models/Dungeon/DungeonSession.cs` (pure, clock and Random injected) and `DungeonRun.cs`; `Games/Managers/DungeonManager.cs` takes and pays money, ticks the session every 1.5 s (each tick moves every crawling run one floor, which animates the dashboard) and publishes the dashboard with buttons. Runs stop at each boss door (floors 5 and 10) to fight, sneak (`DungeonRun.SneakChance` 50%, otherwise the boss strikes first enraged) or drink a potion and fight; a door left 60 s is fought. Potions drop in chests (25%) and quiet corridors (10%) and heal 50% of max HP. Block odds stay about 50/25/12.5% with plain fighting (`DungeonOddsTests`; tune `BlockDifficultyStep` and `MonsterFor`). Typed `.dng` subcommands still work and refusals are posted briefly; button refusals are private.
- Face Off (`.fo`): rules in `Games/BattleArena.cs`, side bets in `Games/Models/BattleArena/SpectatorPool.cs`, Discord flow in `Games/Managers/BattleArenaManager.cs` (one `LiveMessage` dashboard per fight, a gate, and a 1 s timer loop). It reuses the base manager's `Games` list, `BetManager.InitiateBet`/`CancelBet` escrow and `EndGame` results, but not its message-based `Start`/`CreateOrJoin`. Up to 6 fighters; the lobby starts 60 s after the second joins, and a lone lobby is refunded after 5 minutes. Each round picks are private (buttons, ephemeral confirmations; typed picks are deleted where the bot can), revealed together, 30 s per round, and a player who doesn't pick attacks a random opponent. Attack and Gamble hit one chosen target (a private select menu with 3+ fighters). A natural 20 is always the best roll, damage is whole numbers, and after `BattleArena.MaxRounds` (12) the highest HP wins; ties and players who go down together split the pot (`BattleArena.Winners`). Spectators back a fighter (select menu, then an amount modal) until round 1 resolves; backers of the winner share the whole backing pool by stake, or everyone is refunded if nobody backed a winner.
- First gamble of the day (`BetManager.ResolveBet`, tracked by `CoinAccount.LastGambleDate`): d10 roll, a 10 steals 10% of the cash of whoever is 1st on the leaderboard (cash + stocks), unless the roller is already 1st; result is read via `BetManager.TakeDailyRoll`.
- Stocks: `Services/StockService` (singleton) ticks every 5-min UTC slot from the `ChatWorker` minute loop via `CommandManager.RunBackgroundTasks`; risk tiers/swings in `Models/Stock.cs`; `.stocks .buy .sell .portfolio`. Amounts can be a share (`.buy SYMBOL 50%`, `StockService.TryParsePercent`, 0-100%): of cash for buy, short and options (`MaxAffordableContracts(..., cashShare)`), of the holding for sell and cover (rounded down, under one share is refused). Leaderboard ranks cash + stock value. Trades move the quoted price (`Stock.Price` = `FairPrice` × (1 + `Impact`)): impact grows with the square root of the shares traded against the stock's `SharesOutstanding`, fills at the midpoint of before and after plus a fixed 1% spread (buys pay half above, sells receive half below), and impact fades by half each tick. Sells pay a 2% tax on gross value (`Stock.SellTaxRate`) that goes into the jackpot, so churning costs. Tiers 3-6 each hold one random stock (tier 6 is crypto with moon/crash bursts, equally likely and equally big in log terms (`CryptoMoonChance` = `CryptoCrashChance`, steps `CryptoStepMin`..`CryptoStepMax`), and a strong rebound after a crash; keep them balanced), plus rare **mega events** (`CryptoMegaChance`, about one boom and one crash every 2 days each way, `MegaTicks`/`MegaStep`): a log move of at least ln 10 plus an exponential tail up to ln 100,000 (`Stock.MegaSize`: every event is 10x or more, 1 in 10 reaches 100x, 1 in 100 reaches 1,000x, none passes 100,000x), spread over 2 to 6 ticks, then fading back at the normal 3% pull with no special rebound. There is no cap on a boom beyond that, so a season's crypto high is typically hundreds of times its launch price and its low a few tenths of a percent. Crypto's floor is `CryptoMinPrice` (1 cent; others keep $1), prices under a dollar are kept to 4 decimals (`Stock.RoundPrice`, shown with `Stock.FormatPrice`), and its trading impact is uncapped on buys and capped at a 95% drop on sells, filled at the average along the impact curve (`PreviewCryptoTrade`), so a huge order pays for its own impact. Holding crypto therefore has a large positive average return (mean reversion plus rare giant booms); it is not a fair bet, and `OptionPricingTests` only guarantee that its options are priced fairly. Options on crypto are expensive (a 6 hour call costs about 90% of the price) and capped at 20x their strike, picked at random from `StockMarket.Pool` whenever the market is created (`.clear coin`). `.stocks` graphs are green or red by `Stock.AllTimeChange` and take a window like `48h` (`DurationParser`). `.short`/`.cover` lock margin (closed at 2x entry); `.call`/`.put` are cash-settled at-the-money options on the fair price (100 shares each, settled in `StockService.TickIfDue`, paying at most `Stock.MaxOptionPayoutMultiple` (20x) the strike per share; priced as at most 24 hours long, `OptionPricer.MaxPricedTicks`). Option premiums come from `Models/OptionPricer.cs`: it runs the real `Stock.ApplyTick` forward from the stock's current state (fair price vs base, crypto streak and rebound state, the current crash drift from `StockService.CurrentDrift`) with a fixed seed and averages the payoff, then `Stock.OptionPremiumPerShare` adds the 10% house edge (`OptionHouseEdge`) and the 2% fee goes to the jackpot. So calls are dear and puts cheap below a stock's base (and the reverse above), and a quote is cached per state. `OptionPricingTests` re-simulates with other seeds and asserts the house wins on average (premium vs realised payout) for calls and puts across tiers, states and durations; re-run it after changing tick dynamics (`ApplyTick`, reversion, crypto bursts). Shorts and options count in `GetPortfolioValue` and block the jackpot via `HasPositions`. Share counts are `int`: `MaxAffordableShares`/`MaxShortableShares` search in `long` (an int search overflowed with billions of cash and looped forever inside the stock lock), and a holding or short can't pass `int.MaxValue` (`StockMarket.TooManyShares`).
- Live stock thread (`.stocksthread`, `.stocksthread stop`, bot admins only via `RequiresAdmin`): `Services/StockThreadService` opens a public thread (one per server) with ONE live message (`LiveStockThread.BoardMessageId`): an embed with a line per stock (price, 5 minute, 3 hour and all-time change, in `.stocks` order via `StockTickerCard.Ordered`) and one image from `StockTickerCard.BuildBoard`: a row per ordinary stock with its all-time chart on the left and the last 3 hours (`StockThreadService.RecentWindow`) on the right, both as % change like `.stocks` (gold and bonds are in the text only; each panel is green or red by its own change). `RunBackgroundTasks` starts `RefreshIfDue` without awaiting it; after each new stock tick it edits the board in place with a fresh image (the file name carries the tick, so clients don't cache), unarchives the thread if needed, and reposts it if it was deleted. Threads saved before the board (a header plus a message per stock: `HeaderMessageId`, `Tickers`, `LiveStockThread.IsOldLayout`) have those messages deleted and the board posted on their next refresh. Thread and message ids are saved in `stockthreads.json` (`Models/StockThread.cs`), so updates survive deploys. Stopping or moving a thread deletes it (`DeleteQuietly`; without Manage Threads it deletes the bot's messages and archives it). `StockThreads.CleanupVersion` below `CurrentCleanupVersion` makes the next refresh delete every ticker thread the bot owns in every server, open or archived, once. `Services/StockTickerCard.cs` also builds the single-stock card for `.stocks SYMBOL`.
- Raffle: `Services/RaffleService` draws every hourly UTC slot (`SlotMinutes`, from `CommandManager.RunBackgroundTasks`; a larger saved `LastRaffleSlot` from the old 30-minute schedule is reset). Anyone whose last money command (`_moneyCommands` in `CommandManager_Main.cs`, stamped by `CoinService.MarkActive`) was within `EntryWindow` (6h) before the draw's due time (`IsEnteredIn`) is entered, so one action covers the next 6 draws (`EnteredDrawCount`, shown in `.pu`); `ActiveWindow` (24h) is only the pool for attacks and sharing. The winner's power-up from `PowerUpCatalog` (`Models/PowerUp.cs`, 36 of them) goes off straight away (`RaffleService.Activate`, which runs `ApplyUse`; a Copycat's copy goes off too). One that can't go off yet (`BadInputException`, or the winner has a bet open) is kept for 24h, and `RaffleService.ActivateKept` (every minute from `RunBackgroundTasks`, `ActivateKeptAndAnnounce`) tries every kept power-up and sets it off the moment it can (skipping players with a bet open or frozen; each is announced in the last active channel), so `.pu use N` is only a way to try one now. The result is announced in one line (named, not pinged) in the channel of the last money command. `.pu list` shows the catalog. The draw rubber-bands (`PowerUpCatalog.WeightFor` with a `PickContext` from `RaffleService.ContextFor`): each power-up has a `PowerUpCategory`; the top tier (`TopTier`: 3, at most half the board) only draws Boosts, lower players draw Attacks and CatchUp more the lower they are, and CatchUp is 3x when 1st is worth over `RunawayMultiple` (3x) the median active player. Attacks go through `RaffleService.Hit` (Shield refuses them before; Mirror reflects; Golden Parachute cancels the debt part), then `Seize` (cash first, the rest on the victim's debt). CatchUp items (Tax the Rich, Audit, Bailout, Squatters, Leech) skip Shield/Mirror/Parachute and are refused for the top tier. Debuffs (`audited`, `frozen`, `squatted`, `leeched`, `PowerUpCatalog.Debuffs`) sit on the victim's `ActivePowerUps`, with `BeneficiaryUserId` for squat/leech. Hooks: `BetManager.ResolveBet` (`BetBonus`, `PowerUps.SettleWin` skims for Audit/Leech/Toll Booth, records the last loss for Time Machine), `CoinService.AddInterest` (Compound Interest, no interest while audited), `PropertyService.PayRentOneHour` (a squat is on one property, `ActivePowerUp.PropertyId`, the leader's best unsquatted rental; old saves without one squat the first property); a squatted property can't be sold while the squat runs (`PropertyService.SquatIn`, checked in `Sell`, so `.sellproperty`, the sell button and `DebtService` auto-sell, which leaves it out of its plan, all respect it), or selling and rebuying would shake the squatters off, `StockService.Buy/Sell`, the daily steal (Loaded Dice), `Draw` (Rigged Raffle) and `ApplyUse` (Freeze, Echo, `CoinAccounts.LastUsedPowerUpId` for Copycat). Numbers are constants in `PowerUpCatalog`.
- Property: `Services/PropertyService` + `Models/Property.cs`. Houses only, bought with cash (`.buyproperty`, `.sellproperty`, `.property`). Apartments were removed: `PropertyKind.Apartment` stays only so old saves load, and `PropertyService.BuyBackApartments` (each `TickIfDue`) pays any left at full market price. Prices follow one shared index on `CoinAccounts` (stepped once a UTC day; booms and busts last 4 to 8 days at about 2% a day, `PropertyCatalog.TrendPerDay`/`MinTrendDays`, so they show within a season; no ceiling and no ordinary floor, only `PropertyCatalog.IndexFloor` (0.01) so a price never reaches zero; each day also has a fat-tailed random move, `PropertyMarket.Laplace` at `NoisePerDay`, or `ShockScale` on a 4% `ShockChance` day, so a day can move houses 10% to 30% or more either way; a trend saved with a longer length is cut by `PropertyMarket.CutOldTrend`). Buying costs 4.5% stamp duty, selling costs 3%. Every property is always rented out (there is no on/off; old saves' `LetOut` flag is ignored). Rent is paid hourly after an 8% agency fee and 4% vacancy: 3.5% of the current market price per hour (`PropertyCatalog.HouseGrossYieldPerHour`) (`PropertyCatalog.RentPerHour`, `PropertyCatalog.NetRentPerHour` after the fee, `PropertyService.PayRentOneHour`; `.portfolio` shows the hourly total, less any squatted property). Prices update once a UTC day, and rent follows them. Holding costs (1% of the current value an hour, `PropertyCatalog.HoldingCostPerHour`) are charged with the rent each hour (`PayHoldingOneHour`). Property counts in net worth at its after-selling-costs value (`CoinService.PropertyValue`) and blocks the jackpot, like stocks. Constants are in `PropertyCatalog`. Debt: `CoinAccount.Debt` is counted against net worth and grows 10% every hour (`CoinAccount.HourlyDebtInterest`, in `CoinService.AddInterest`). Blue Shell and Pickpocket take a share of the victim's net worth: their cash first (`RaffleService.Seize`), and any shortfall goes on their debt. Stock and property sale proceeds pay debt first (`CoinAccount.PayDebtFrom`), and any spare cash pays debt automatically every minute (`CoinService.RepayDebtsFromCash`, skipping players with a bet open). Players with `CoinAccount.AutoSellForDebt` on (`.autosell on`) then have assets sold for what's left (`Services/DebtService`, planned by `DebtService.Plan`: stocks first, the biggest holding first and only as many shares as needed; then the cheapest property that covers the rest, else the most valuable; shorts and options are left alone). Selling moves the price, so one plan can fall short: `AutoSellForDebts` plans and sells again from the new prices (`SellRound`, up to `DebtService.MaxRounds`) until the debt is zero or nothing sellable is left.
- Market crashes (the GFC): `Models/MarketCycle.cs`. The daily roll (once a UTC day while the market is normal, in `PropertyService.TickIfDue`) is `MarketCycle.ChanceFor(exposure)`: `DailyChance` (1/20, about one crash every 4 weeks counting the 7 day cycle, so about one a season, and about one every 11 days when fully invested) up to `MaxChanceMultiple` (5x) as the share of all player wealth in ordinary stocks and houses rises to `FullExposureShare` (60%). `StockService.RiskyAssetShare()` computes that share (gold and bonds count in the total only, so they never raise it) and is passed in lazily from `CommandManager.RunBackgroundTasks`. A crash rolls a severity when it starts (`CoinAccounts.CrisisSeverity`, `r*r`, so mostly moderate) and runs Decline (2 days), Bottom (1) and Recovery (4), so a whole crash fits in a season. Ordinary stocks fall from 38–50% by tier (60% crypto) at severity 0 to 70/80/90% (99% crypto) at severity 1, houses 25% to 70% (`MarketCycle.FallFor`, `PropertyFall`; the index has no limit but `PropertyCatalog.IndexFloor`). Recovery gives back `RecoveryShare` (85%) of the loss in log terms, so prices end below where they were; `StockService.TickIfDue` applies the drift each tick via `MarketCycle.DriftFor(stock, phase, severity)`; during a crash an ordinary stock is pulled (at the normal reversion rate) towards `Stock.CrisisAnchor`, its price when the crash began moved by the drift each tick, not towards its base, and `Stock.NoiseDrag` cancels the noise's own downward pull in log terms, so the typical stock falls by the stated amount and the spread stays as narrow as in normal trading (a free random walk without this took a mild crash far past its fall; `MarketCrashTests.ADecline_FallsByItsStatedAmount…` guards it; crypto just follows the drift), and once the crash ends stocks keep their new level as their base (`ResetBasePrices`). A phase saved under older lengths is cut to the current length. Headlines (including how bad it is) go to the last few active channels (`CommandManager.PostToRecentChannels`). Phase state lives on `CoinAccounts` (`MarketPhase`, `NextCrisisAllowedDay`, `CrisisSeverity`).
- `.convo` (`Models/ConvoModel.cs`, `Services/ConvoCorpusService.cs`): the first scrape starts by itself once the bot is connected and nothing was ever scraped (`EnsureScrapeStarted` from the minute loop, `ShouldAutoScrape`), and `.scrapeconvo` (bot admins; `status`, `stop`) runs it again. It downloads, in the background, every message the bot can read in server `ConvoCorpusService.GuildId` except channel `ExcludedChannelId` (and its threads, or a category's channels): text, news and voice chats, open threads and archived public threads. It writes them to `convo_data/messages/<channelId>.tsv` in the bot's working directory on the Pi (`id\tusername\ttext`; never in the gist or the repo), saves its place per channel in `convo_data/scrape_state.json` after every 100-message page (`PagePause` between pages), and later runs only fetch new messages. It does a quick pass first (the newest `QuickPassPages` pages of every channel, then a model reload) and then the full history, rebuilding the model every `ReloadDuringScrape` (15 minutes) as it goes. `Clean`/`Extract` drop bots, system messages, bot commands, code blocks, links and @everyone, and resolve mentions to plain names. `ConvoModel` is a word Markov chain per person (`Chain`: entries grouped by speaker and sorted by context, so every line is built from its speaker's own messages; two words of context, one word of their own `Chaos` (40%) of the time, which makes it unhinged; everyone's one-word chain only bridges a word the speaker never used, such as a seed, and people with under `MinOwnMessages` borrow it for the chaos steps), about 30 bytes a word, built in the background at startup (`EnsureLoadStarted` from the minute loop) and after each scrape from at most `MaxMessages` (a random sample above that). Messages from `FavouredChannelIds` (`ConvoMessage.Favoured`, from the file name via `IsFavoured`) make up `FavouredShare` (`ConvoModel.DefaultFavouredShare`, 95%) of every choice whenever they have one, whatever their size: each person's chains are split into two pools (`Group` = speaker and pool) and every next word, opening word and run start takes the favoured pool 95% of the time (`PickPool`, `TryPickOwn`, `RunStart`), falling back to the other pool when it has nothing. Under `MaxMessages` the favoured channels are kept whole and the rest sampled into what's left, and those channels are scraped first. A convo is 3 to 10 lines (`MinLines`/`MaxLines`) of `user: text`: speakers come from a real run of messages in one channel, each line starts with a word its speaker really opens with or picks up a word from the line before that the speaker also uses (`ReplyHookChance`, `OwnStartChance`), and `.convo words` steers the first line, which carries on from the words as if they had just been said, without showing them. In that server it only ever answers from the model, never the LLM: before the history is in, it says it's loading or reading (and starts the scrape if none is running). In other servers the old Ollama prompt (`ConvoService`) runs off the gateway task with a 60 s timeout, and only lines matching `ConvoService.KeepChatLines` (`name: text`, a name without spaces) are posted, at least 3 or it retries (`LlmConvoTries`). It's sent with no mentions allowed.
- Recent channels and patch notes: `CoinService.MarkActive` keeps `CoinAccounts.RecentActiveChannelIds` (the last 3 channels money was used in, newest first; `CoinService.RecentChannels()` falls back to `LastActiveChannelId` on old saves). Market news and the post-update patch notes go to all of them. After a restart `CommandManager.AnnouncePatchNotesIfNew` (once per process, from the minute loop, when connected) compares `CoinAccounts.LastAnnouncedPatch` with the newest note (`PatchNotes.KeyOf`, `NewSince`): new notes (up to 8) are posted, nothing is posted when none are new or on the very first run (it only records the marker). The marker is saved before posting.
- Tiers 1 and 2 hold only safe havens: `BOND` is tier 1 and `GOLD` is tier 2. Old markets that still had an ordinary stock there are migrated on load (`StockMarket.SchemaVersion`, `StockMarket.Retire` pays holders out at current value).
- Safe havens: `GOLD` rises 20% during a decline and fades back to its base after; `BOND` pays 0.1% an hour (`Stock.BondGrowthPerHour`) with almost no swing. Both are always listed (`StockMarket.SafeHavens`, `Stock.Role`), not drawn from the random pool, and trade with `.buy`/`.sell`.
- Money: `Services/CoinService` (accounts, interest, leaderboard) + `Managers/BetManager` (initiate/resolve bets, bonuses, stats). Jackpot: 75% of every lost bet (`BetManager.JackpotLossShare`, taken in `ResolveBet` from `betAmount - totalWinnings` after the roll; Face Off passes `feedJackpot: false` through `BaseMultiplayerManager.LossesFeedJackpot` because its losers' money already goes to the winner; dungeon buy-ins lost on a death, a PvP loss or a cash out below the buy-in come from `DungeonSession.TakeForfeits`), sell tax, the 20% donation tax and every debt repayment go into `CoinAccounts.JackpotPool` (debt is paid through `CoinAccounts.PayDebtFrom(account, amount)` / `RepayFromCash(account)`, or `AddDebtRepaymentToJackpot` for Bailout, never the bare `CoinAccount` methods). When a bet qualifies (`BetManager.QualifiesForJackpot`: all the player's cash up to `JackpotSmallBetLimit` ($10,000), or `JackpotBigBetShare` (half their cash) or more on a bigger bet) with no stocks or property held, `BetManager.ResolveBet` rolls `JackpotWinChance` (3%) to pay the pool out, at most `JackpotRollsPerHour` (10) rolls per player per UTC hour (`TryUseJackpotRoll`, saved on the account; a capped bet gets a note through `TakeJackpotWin`). Three 💎 on `.slots` also win it. Persistence via `Common/Services` (`GistService` remote, `LocalFileService` local).

## Adding things
- **New command**: write handler in the matching `CommandManager_*.cs`, then register it in the `_commands` list in `CommandManager_Main.cs` (comment there says so).
- **New service**: create in `DiscordBot/Services/`, register in `Startup.ConfigureServices`, inject into `CommandManager` ctor if commands need it.
- **New game**: Game + Manager + Player model, register Manager singleton in `Startup`, add handler in `CommandManager_Games.cs`.

## Conventions / gotchas
- **Game time is fast.** A season (a `.clear coin` market and accounts) lasts 2 to 4 weeks, and the economy runs in hours (rent 3.5% an hour, interest 2% an hour, debt 10% an hour, stock ticks every 5 minutes). Anything slow must be scaled to that, not to the real world: crash cycles last days, property swings days, bond yield and holding costs are hourly, options run 15 minutes to 3 days and are priced by simulating the game's own tick process. Don't use real-world yearly rates or month-long cycles.
- Files use UTF-8 BOM and namespaces matching folders (note: `DiscordBot.Exceptions` namespace is used for exceptions that live in `Common/Exceptions`).
- Hardcoded admin/bot IDs live in `CommandManager_Main.cs` (`_adminIds`, `_botId`); blacklists in `appsettings.json` (`AppSettings.cs`).
- Discord message limit 2000 chars (`_messageCharLimit`); keep replies under it. Embeds are capped at 6000 chars total and 1024 per field, so long lists go through `TextPaginator.Paginate` (`Common/Helpers/TextPaginator.cs`) and send one embed per message, as `.help` does.
- `mappings.json` / `reminders.json` are runtime data copied to output.
- Patch notes: a significant change gets a one-line entry at the top of `PatchNotes.All` (`Models/PatchNotes.cs`); `.patchnotes` shows them.
- Branch `gambling-rework` is active; `master` is the deploy branch.
